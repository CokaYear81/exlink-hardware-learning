## 本章起点

当最后一个焊点完成时，板子仍然不会自动变成一台调试器。ESP32-S3、CH549 和 RP2040 都需要各自的固件，电脑还要通过正确的 USB 模式识别它们。

这一阶段让我真正看到软件和硬件的交界：源代码需要经过编译和链接成为固件，芯片要进入特定启动模式，数据才能通过 USB 写入 Flash；重新启动后，Bootloader 再决定怎样加载程序。任何一环不成立，最终看到的都可能只是“烧录失败”或“屏幕没有反应”。

## ESP32-S3：从工程到运行界面

现有工程使用 PlatformIO，目标环境是 ESP32-S3，并明确固定了平台版本：

```ini
[env:esp32s3]
platform = espressif32 @ 6.5.0
board = esp32-s3-devkitc-1
framework = arduino
board_build.arduino.partitions = my.csv
board_build.arduino.memory_type = qio_opi
build_flags = -DBOARD_HAS_PSRAM
board_upload.flash_size = 16MB
```

这段配置让我意识到，编译环境不是一个可以忽略的背景条件。芯片型号、Flash 大小、PSRAM、分区表和框架版本都会影响最终生成的固件。代码完全相同，也可能因为依赖版本不同而产生编译错误或运行异常。

### Boot 模式与 Flash

按键和启动配置脚决定 ESP32-S3 是进入正常启动还是下载模式。烧录完成后，Flash 中不只有“我的程序”，还可能包括 Bootloader、分区表、固件和持久化数据。

过去我把“把代码传到开发板”看成一个按钮动作。现在我更愿意把它理解成一条完整链路：

```text
电脑上的工程
  -> 编译与链接
  -> 生成固件映像
  -> 芯片进入下载模式
  -> USB 传输并写入 Flash
  -> 复位
  -> ROM 与 Bootloader 加载用户程序
```

## RP2040：UF2 让烧录过程变得可见

RP2040 进入 Boot 模式后会被电脑识别成存储设备，把 UF2 固件复制进去后自动完成写入。这是三个烧录流程中最直观的一种，也让我看到了“同一个 USB 接口在不同阶段可以枚举成不同设备”。

逻辑分析仪固件烧录完成后，还需要在电脑端配置驱动并由 PulseView 连接。到这里，固件、USB 设备、驱动和上位机软件才组成了一条完整的使用链。

## 串口日志成为硬件排查工具

程序运行后，串口日志把芯片内部状态暴露给了电脑。如果界面没有正常出现，日志可以帮助判断程序是否启动、某个 I²C 设备是否被识别、初始化停在哪一步。

这让我逐渐建立了分层判断方式：

1. 电脑有没有识别 USB 设备？
2. 芯片能否进入下载模式并完成写入？
3. 复位后程序有没有真正开始运行？
4. 串口日志指出哪个外设初始化失败？
5. 对应外设的供电、焊接、地址和通信线路是否正确？

软件报错不一定只靠改代码解决，它也可能是硬件没有回应程序的结果。

## 阶段小结

这一阶段让我意识到，嵌入式程序从来不是孤立运行的软件。它依赖电源、引脚、外设、存储器、驱动和通信协议。能够在代码日志和真实电路之间来回定位问题，是我从这次烧录过程中得到的最大收获。
